# Верификатор: разбор отказов и план теста

Данные: `runtime/request-journal.sqlite3`, 152 запроса с 30.09 по 08.10.2026. В основном это пробные запросы при разработке, разные версии кода, некоторые вопросы повторяются (аннуитет — 6 раз). Выводы о частоте поэтому приблизительные; о характере ошибок — надёжные.

Эталоны, по которым проверялись ответы:
- аннуитетный платёж 1 000 000 ₽, 60 мес., 1 %/мес. = **22 244,45 ₽**;
- 17 · 23 + 144 / 12 = **403**;
- 15.04.2024 — **понедельник**;
- дата сервера в момент запросов — 06.10.2026, она передаётся модели в системном промпте.

## 1. Итог

Верификатор вынес отказ (RETRY или FAIL) в 20 запросах, всего 67 вердиктов.

| Оценка вердикта | Кол-во | Доля среди оцениваемых (42) |
|---|---:|---:|
| Обоснованный: ответ действительно неверен, причина названа верно | 15 (2 из них — проверка кодом) | 36 % |
| Ответ плохой, но названная причина ложная | 4 | 10 % |
| Ложный или необоснованный отказ | 22 (18 — ответы с веб-источниками) | 52 % |
| Сбой самого верификатора (невалидный JSON → FAIL) | 1 | 2 % |
| Не определить: текст ответа не сохранён | 25 | — |

Что стало с запросами:
- **10 закончились HTTP 500** (9 в чате, 1 у агента). Минимум в 5 из них причина — ложный отказ или сбой верификатора: № 7, 11, 15, 16, 18. В № 11 последний отклонённый ответ был верным.
- **7 запросов в чате прошли после повторов, и в 3 из них принят неверный ответ** (№ 5, 12, 19). В № 5 неверное число подсказал сам верификатор.
- Верный итоговый ответ после повтора подтверждается только в одном запросе (№ 8). Ещё в двух (№ 4, 20) он вероятен.

## 3. Закономерности

**Ложные отказы**
1. **Споры о фактах, которых верификатор не видит** (18 из 22). Он получает только заголовки и URL источников, а требует убрать или добавить факты. Поправка `sourced_answer_dispute` закрывает это для `result` и `completeness`. Отказы с `issue=format` по-прежнему проходят (№ 16).
2. **Требует язык, на котором ответ уже написан** (№ 14, 17, 19). Закрыто поправкой `language_already_used`, но у неё побочный эффект: бессмысленный ответ на правильном языке проходит (№ 19).
3. **Неверная эвристика сравнения чисел** (№ 11). Исправлено.
4. **Бессмысленные замечания**: исправление совпадает с оригиналом (№ 2), жалоба на собственные входные данные (№ 16). **Не закрыто.**
5. **Сбой разбора ответа верификатора** превращается в FAIL и HTTP 500 (№ 7). **Не закрыто.**

**Вред от подсказок, даже когда отказ верен**
Верификатор выдумывает «правильные» формулы (№ 3, 11), числа (№ 5) и даты (№ 13). Модель копирует подсказку, и её ответ принимается (№ 5). Новые числа теперь скрываются, но формулы и даты — нет.

**Повтор редко исправляет ответ**
Даже после обоснованного отказа модель обычно делает другую ошибку (№ 11, 12, 13, 19). Верный итоговый ответ подтверждается в 1 случае из 17, вероятен ещё в 2.

## 4. План теста

Вопрос теста: окупает ли проверка моделью около +60 % времени на попытку и риск HTTP 500 приростом итогового качества — и в каких категориях. Критерии решения задаются до прогонов (шаг 6).

### Шаг 0. Логирование (обязательно перед всем остальным)
Сейчас 25 из 67 вердиктов не оценить: `candidate_preview` сохраняется только для отклонённых ответов и только 400 символов, текст источников и картинки не хранятся.
- Сохранять полный текст **каждой** попытки, включая принятую, вместе с вердиктом, `issue`, `feedback` и `override`.
- Для веб-ответов сохранять текст источников, который видела генерация. Для картинок — хеш и путь в локальном кеше.
- Ограничить размер, чтобы журнал из 200 записей не разрастался.

### Шаг 1. Расширить размеченный набор `core/tests/data/verifier_cases.jsonl`
- Из этого разбора, где ответ сохранён: № 11 (все пять попыток), № 12 (1–4), № 13 (1–5), № 14 (1–5), № 16-5, № 17-1, № 18-3 и 18-4 (честное «в источниках нет» — верный ответ), № 19 (1–3), № 2.
- Добавить категории, которых нет или почти нет:
  - **финальный текст агента** (`verify_agent`) — сейчас 0 случаев;
  - веб с **полным текстом** источников;
  - дата и время;
  - «дай только число» (формат);
  - картинки.
- Новое поле для каждого случая: подсказка не должна содержать чисел, формул или дат, которых нет в запросе. Так измеряется вред от подсказок.
- Цель — около 120 случаев, не меньше 10 на категорию.

### Шаг 2. Офлайн-оценка верификатора (минуты)
```bash
.venv/bin/python scripts/verifier_eval.py --llm stub
.venv/bin/python scripts/verifier_eval.py --llm live --baseline HEAD
```
- Прогнать на 9B и на 4B.
- Метрики по категориям: ложные принятия, ложные отказы, вредные подсказки, невалидный JSON.
- Сравнить три варианта: только код; код + модель; код + модель везде, кроме веба.

### Шаг 3. Модульные тесты на найденные дефекты (без модели)
- Исправление совпадает с оригиналом → не отказ (№ 2).
- Замечание о полях входных данных верификатора (`web_sources`, `candidate`, `messages`) → не отказ (№ 16).
- Невалидный JSON верификатора → не HTTP 500 (№ 7).
- Поправка «язык уже верный» не должна принимать ответ, если модель-верификатор при этом указала ошибку смысла (№ 19).
- Одна и та же подсказка дважды подряд → остановить повторы.

### Шаг 4. Сквозной A/B (часы)
- **Варианты:** A — как сейчас; B — `--no-verify`; C, если реализовано, — одна попытка по замечанию модели и без HTTP 500 (вернуть последний ответ с пометкой).
- **Как сэкономить прогон:** при `temperature 0` и полном логировании попыток (шаг 0) первая попытка варианта A и есть ответ варианта B. Достаточно одного прогона A. Совпадение проверить настоящим прогоном B на 30 вопросах.
- **Данные:**
  - GSM8K, 200 вопросов, и MMLU-Pro, 200 вопросов, через `scripts/benchmark.py`;
  - «живой» набор из 60 запросов с эталонами: перевод, извлечение в JSON, дата, новости с замороженными источниками, картинки.
- **Метрики:**
  - точность, где HTTP 500 считается неверным ответом;
  - доля исправленных: первая попытка неверна, итог верен;
  - доля испорченных: первая попытка верна, итог неверен или HTTP 500;
  - доля HTTP 500;
  - время p50 и p90, токены.
- **Статистика:** тест McNemar уже есть в `benchmark.py`. На 200 вопросах 95-процентный интервал точности около ±6 п.п. Парный тест заметит разницу около 5 п.п., если ответы двух вариантов расходятся примерно в 10 % пар.

### Шаг 5. Путь агента (по желанию)
- `verify_agent`: 30 размеченных финальных отчётов из сессий OpenCode — честный отчёт; «тесты прошли» без подтверждения в истории; ответ не на том языке.
- Вызовы инструментов: на 10–20 задачах OpenCode посчитать явно ошибочные или лишние вызовы, которые сейчас проходят без проверки моделью. Это покажет, нужна ли она там.

### Шаг 6. Критерии решения (зафиксировать до шага 4)
- **Проверка моделью остаётся в категории, если одновременно:**
  - доля исправленных минус доля испорченных — не меньше 3 п.п.;
  - разница значима (McNemar, p < 0,05);
  - доля HTTP 500 не растёт.
- **Иначе — выключить проверку моделью для этой категории** (флаг в `response_policy.json` эксперта) и оставить проверки кодом.
- **Факты в веб-ответах моделью не проверять**, пока верификатор видит только заголовки и URL источников.
- **В любом варианте:**
  - когда попытки кончились — отдавать последний ответ с пометкой «не подтверждён», а не HTTP 500;
  - невалидный JSON верификатора → принять ответ с пометкой.

## 5. Результаты (09.10.2026)

### Компонентный тест: верификатор на готовых ответах
Набор расширен до 76 случаев (43 неверных ответа, 33 верных); 13 новых взяты из разбора выше.

| | Только код | Код + модель 9B | Код + модель 4B |
|---|---:|---:|---:|
| Поймано неверных ответов | 18 из 43 | 36 из 43 | 35 из 43 |
| Отклонено верных ответов | 0 из 33 | 1 из 33 | 2 из 33 |

- Старые ложные отказы на ответах «нет доступа к новостям» и «в источниках этого нет» больше не повторяются.
- Ошибки теперь пропускают поправки кодом: `language_already_used` принимает бессмысленный ответ, если верификатор придрался к языку; `sourced_answer_dispute` принимает ответ не по теме.

### Сквозной A/B: GSM8K, режим `auto`, `temperature 0`, 9B на MLX
- Прогон с верификатором: 71 вопрос, остановлен на 71 из 100.
- Прогон без верификатора: заново прогнаны только 6 вопросов, где верификатор требовал повтор. На остальных 65 ответ без верификатора равен ответу, принятому с первой попытки. Это подтверждено на 6 контрольных вопросах из 6.

| | С верификатором | Без верификатора |
|---|---:|---:|
| Точность | 62 из 71 (87,3 %) | 62 из 71 (87,3 %) |
| Верно только в этом варианте | 0 | 0 |
| HTTP 500 | 1 | 0 |
| Общее время | 69 мин | ≈ 49 мин |

- **Где был повтор (6 вопросов):**
  - в 4 случаях верификатор отклонил верный ответ, причём дважды подсказал неверное (число 318 вместо 319; «умножь на 3» вместо «на 2»);
  - в 2 случаях ответ был неверным, но повтор его не исправил: в одном снова неверный ответ, в другом HTTP 500.
- **Пропущенные ошибки:** из 8 неверных ответов, где рассуждение уложилось в лимит токенов, верификатор поймал 1, исправил 0.
- **Цена по времени:** около +42 %. Сами вызовы модели-верификатора — 6,5 мин (84 вызова, медиана 3,8 с). Остальное — повторы: 21 мин против 5,5 мин на 6 вопросах.
- **Статистика:** McNemar p = 1,0. Ни одного спасённого ответа из 71, значит, с 95-процентной уверенностью выигрыш на таких задачах не больше ~4 п.п. (правило трёх: 3/71).

**Вывод для математики и рассуждений (`reasoning_expert`):** проверка моделью не повышает точность, добавляет около 42 % времени и HTTP 500.
- На размеченном наборе модель ловит 36 из 43 ошибок, а на реальных ошибках GSM8K — 1 из 8.
- Причина: в наборе ошибки грубые (неверная дата, другой язык, выдуманные поля). Тонкую ошибку в рассуждении модель того же размера не видит.

Не проверено сквозным замером: перевод, извлечение в JSON, даты, веб. Там компонентный тест показывает пользу проверки моделью, но исправляют ли ответы повторы — неизвестно.

## 6. Решение (09.10.2026)

Проверка моделью отключена. Ответ проверяется только кодом:
- ответ не пустой и не обрезан;
- нет мета-комментария вместо ответа;
- ссылки `[n]` ведут на реальные источники;
- арифметика из запроса сходится;
- поля JSON — только запрошенные и взятые из входного текста;
- у агента — валидный по схеме вызов инструмента и необрезанный финальный текст.

Код модели-верификатора остался в `core/verifier_v6.py` за флагом `review=True`. Его вызывает только `scripts/verifier_eval.py`, чтобы проверку моделью можно было измерить снова.
